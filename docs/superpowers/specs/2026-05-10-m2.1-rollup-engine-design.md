# M2.1 — Rollup Engine Design

**Phase:** 2 — Rollups + retention
**Milestone:** M2.1 (rollup engine + `rebuild-rollups` command)
**Date:** 2026-05-10
**Status:** Approved (pending implementation plan)

## Goal

Maintain `sessions` and `prompts` rollup tables in lockstep with the `events` table. Every event written by the ingest path also updates the relevant rollup row inside the same SQLite transaction. A `cco rebuild-rollups` command can recompute rollups from scratch by replaying all events.

## Out of scope (deferred to other milestones)

- Session idle-timeout sweeper (M2.2)
- Retention pruner (M2.3)
- TUI consumption of rollups (Phase 3)

## Architecture

Three packages collaborate. Rollup logic is a pure function package; the SQL execution boundary lives in repository where the transaction already exists; the service layer stays thin.

### `internal/rollup/` (new — pure, DB-agnostic)

```go
type Op struct {
    Query string
    Args  []any
}

type Updater func(ev domain.Event) []Op

var updaters = map[string]Updater{
    "session_start":  applySessionStart,
    "session_end":    applySessionEnd,
    "user_prompt":    applyUserPrompt,
    "api_request":    applyAPIRequest,
    "api_error":      applyAPIError,
    "tool_decision":  applyToolDecision,
    "tool_result":    applyToolResult,
}

// Apply returns the SQL ops for an event. Returns nil for unknown event names
// (forward-compatible: new event types do not break ingest).
func Apply(ev domain.Event) []Op
```

One file per event type (`api_request.go`, `api_error.go`, `tool_decision.go`, `tool_result.go`, `user_prompt.go`, `session_lifecycle.go`). Each file exports only its updater function. Tests live next to it (`api_request_test.go`, etc.).

### `internal/repository/` (extended)

Two new methods on `*Repository`:

```go
// InsertEventsAndApplyRollups inserts events and applies all rollup updates
// in a single transaction. This is the new live-ingest path.
func (r *Repository) InsertEventsAndApplyRollups(ctx context.Context, events []domain.Event) error

// RebuildRollups truncates sessions and prompts, then replays every event in
// (ts, id) order through the rollup updaters. Single transaction.
func (r *Repository) RebuildRollups(ctx context.Context) error
```

The existing `InsertEvents` stays for tests and tools that do not want rollups.

### `internal/service/` (one-line change)

`Service.IngestLogs` swaps `repo.InsertEvents(...)` for `repo.InsertEventsAndApplyRollups(...)`. No other changes.

### `cmd/app/` (new subcommand)

A `rebuild-rollups` subcommand opens the DB, calls `repo.RebuildRollups(ctx)`, prints `rebuilt: N events → M sessions, K prompts (elapsed: …)`. Documented as "stop `cco serve` first."

## Transaction & call-site model

One SQLite transaction per OTLP batch. Either every event insert and every rollup op lands, or nothing does. Rollup bugs surface as failed `tx.Exec` calls that roll back ingest and propagate to the OTLP client (which retries).

```
OTLP request
  → service.IngestLogs: parse → []domain.Event
  → repo.InsertEventsAndApplyRollups(ctx, events)
       BEGIN
       insertEventsTx(tx, events)            -- existing helper
       for ev in events:
         for op in rollup.Apply(ev):
           tx.Exec(op.Query, op.Args...)
       COMMIT  (ROLLBACK on any error)
```

## Updater behaviors

All UPSERTs use SQLite `INSERT … ON CONFLICT (pk) DO UPDATE SET …`. Every updater also bumps `sessions.last_seen_at = MAX(last_seen_at, ev.ts)` so the M2.2 sweeper has fresh data.

### Auto-create on demand

Any event referencing an unseen `session_id` auto-creates the `sessions` row with `started_at = ev.ts`, `last_seen_at = ev.ts`, all counters at the increment value. Metadata columns (`project_name`, `project_cwd`, `app_version`, `os_type`, `user_id`) stay NULL until `session_start` arrives. Same pattern for `prompts` rows when `user_prompt` is missing or out of order.

This makes the system robust to OTLP batch reordering and to a `session_start` arriving after other events for the same session.

### Per-event-type rules

**`session_start`** — UPSERT sessions: insert with `started_at`, `last_seen_at`, and metadata fields from attrs. On conflict (auto-created earlier), fill metadata fields *only when currently NULL* and set `started_at = MIN(started_at, ts)`.

**`session_end`** — UPDATE sessions: `ended_at = ts`. No prompts touch.

**`user_prompt`** — two ops:
1. UPSERT prompts: `prompt_id`, `session_id`, `started_at = ts`, `prompt_length`, `command_name`, `command_source` from attrs. On conflict, fill those fields if NULL.
2. UPSERT sessions: `prompts = prompts + 1`, plus `last_seen_at` bump.

**`api_request`** — two ops:
1. UPSERT sessions: increments `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `cost_usd`, `api_requests`. If `attrs.query_source = 'subagent'`, also `subagent_requests += 1`. (`auxiliary_requests` is bumped if the parser emits the corresponding attr; exact attr name to be verified in implementation.)
2. UPSERT prompts (only when `prompt_id` is non-empty): same token + cost increments + `api_requests += 1` + `subagent_requests += 1` (when applicable).

**`api_error`** — two ops:
1. UPSERT sessions: `api_errors += 1`.
2. UPSERT prompts (only when `prompt_id` is non-empty): `had_error = 1`.

**`tool_decision`** — UPSERT sessions: `tool_denied += 1` *only when* `attrs.decision = 'deny'`. No prompt op (denial isn't strictly per-prompt for this rollup, and the ROADMAP gate doesn't require it).

**`tool_result`** — two ops:
1. UPSERT sessions: `tool_calls += 1`.
2. UPSERT prompts (only when `prompt_id` is non-empty): `tool_calls += 1`.

### Missing `prompt_id` policy

When an event that *could* update a prompt arrives without `prompt_id`, the prompt op is skipped; the session op still applies. Logged at debug level only — not an error.

## `rebuild-rollups` semantics

```
BEGIN
DELETE FROM prompts;
DELETE FROM sessions;
SELECT id, ts, session_id, prompt_id, event_name, attrs
  FROM events
  ORDER BY ts ASC, id ASC;            -- streamed via Rows.Next()
for each row:
  decode attrs JSON into domain.Event
  for op in rollup.Apply(ev):
    tx.Exec(op.Query, op.Args...)
COMMIT
```

Single transaction. After completion, rollup totals exactly match what live ingest would have produced. Stop `cco serve` first; no concurrent-write safety needed.

The `(ts, id)` ordering matters: OTLP batches can carry multiple events with identical `ts`, and we rely on the events table's autoincrement `id` for tie-breaking. Live ingest writes events in receipt order, which `id` preserves.

## Error handling

- **Parse error in service** → existing behavior unchanged (drop record or 5xx).
- **Bad SQL from a rollup updater** → `tx.Exec` fails, tx rolls back, ingest returns error → OTLP client retries. This is a programmer bug; tests catch it before it ships.
- **Unknown `event_name`** → `Apply` returns `nil`; no error. Forward-compatible with future parser additions.
- **Missing `prompt_id`** on a prompt-touching event → skip the prompt op; session op still applies; debug log only.

## Testing

Coverage target: **≥ 90% on `internal/rollup/`** (ROADMAP gate).

- **`internal/rollup/<event>_test.go`** — table-driven, no DB. Pass synthetic `domain.Event`, assert on returned `[]Op` (query string + args). Cover all ROADMAP gate cases: subagent flag, `decision = deny` vs other, missing `prompt_id`, etc.
- **`internal/rollup/registry_test.go`** — `Apply` returns nil for unknown event names, returns the expected updater for known names.
- **`internal/repository/rollups_test.go`** — integration on temp SQLite. Feed a synthetic event sequence through `InsertEventsAndApplyRollups`, assert on resulting rows. Documents that re-applying the same batch doubles counters (this is the correct behavior — UPSERTs are not idempotent across separate batches; idempotency is provided at the rebuild level by truncating first).
- **`internal/repository/rebuild_test.go`** — seed events table directly, run `RebuildRollups`, assert rollup totals match what `InsertEventsAndApplyRollups` produced for the same events. Truth check per ROADMAP demo.
- **`internal/service/integration_test.go`** — extend existing test: send OTLP request with mixed events, assert on `sessions`/`prompts` end state.

## Demo (ROADMAP M2.1 acceptance)

- A hand-fed synthetic event sequence produces correct `sessions` row (all token, cost, request, error, tool counters and `prompts` count).
- The same sequence produces correct `prompts` rows with per-prompt totals and `had_error` flag.
- `./bin/cco rebuild-rollups` on an M1.3 database produces the same totals as live ingestion did.
- `SUM(cost_usd)` on `sessions` equals the sum of `cost_usd` JSON-extracted from `events` of name `api_request` (truth check).
