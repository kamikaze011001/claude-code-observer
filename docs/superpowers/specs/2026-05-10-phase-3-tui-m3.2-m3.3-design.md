# Phase 3 TUI — M3.2 + M3.3 Design

> Combined design for **M3.2 Sessions list + Session detail** and **M3.3 Prompt detail**.
> Builds on the M3.1 shell (page-stack `App`, `theme`, `readstore` read-only pool).

## Goal

From the dashboard, navigate down to a per-session event timeline and from there into a per-prompt breakdown. Drill: Dashboard → Sessions → Session Detail → Prompt Detail. `b` walks back up the stack with selection preserved.

## Architecture

Two new packages under `internal/tui/`:

- **`internal/tui/sessions/`** — two `app.View` implementations:
  - `List` (M3.2 page 1): paged list of sessions newest-first.
  - `Detail` (M3.2 page 2): flat chronological event timeline for a chosen session.
- **`internal/tui/prompt/`** — one `app.View` implementation:
  - `Detail` (M3.3): rollup numbers + tool calls + api_requests for a chosen prompt.

Read access goes through `internal/tui/readstore/` (the existing read-only pool from M3.1). Three new query functions are added there. No changes to `app/`, `theme/`, or `repository/`.

The dashboard gets a single new key (`s`) that pushes `sessions.NewList(pool)`. From that point, all navigation lives inside the page-stack:

```
Dashboard ── s ──▶ Sessions List ── enter ──▶ Session Detail ── enter (on user_prompt) ──▶ Prompt Detail
                                  ◀────── b ──────────────── b ─────────────────────── b ──
```

State is preserved across `b` because each `View` is a heap-allocated struct held by the App's stack — popping does not destroy the underlying page.

## Data Layer

All three queries reuse the existing read-only pool (`mode=ro` + `query_only(1)` + WAL) and the 500ms-context-timeout pattern from M3.1.

### `SessionsPage(ctx, db, cursor *int64, limit int) ([]SessionRow, *int64, error)`

```sql
SELECT session_id,
       project_name,
       started_at,
       last_seen_at,
       ended_at,
       cost_usd,
       prompts
FROM sessions
WHERE (? IS NULL OR started_at < ?)
ORDER BY started_at DESC
LIMIT ?;
```

- `cursor` is a `started_at` value (unix ns); `nil` means "first page".
- Returns rows plus the next cursor (`= last row's started_at`, or `nil` if `len(rows) < limit`).
- `SessionRow` fields:
  - `SessionID string`
  - `ProjectName string`  // empty string rendered as `(unlabeled)`
  - `StartedAt time.Time`
  - `DurationSec int64`   // `(coalesce(ended_at, last_seen_at) - started_at) / 1e9`
  - `CostUSD float64`
  - `Prompts int64`
  - `Live bool`           // `ended_at IS NULL`

Default `limit = 50`.

### `SessionEvents(ctx, db, sessionID string, beforeTS *int64, limit int) ([]EventRow, bool, error)`

```sql
SELECT ts, event_name, prompt_id, attrs
FROM events
WHERE session_id = ?
  AND (? IS NULL OR ts < ?)
ORDER BY ts DESC
LIMIT ?;
```

- Returns rows plus `hasMore` (`= len(rows) == limit`).
- `EventRow` fields:
  - `TS time.Time`
  - `EventName string`
  - `PromptID string`     // empty if session-level
  - `Summary string`      // built in Go (see below)

Default `limit = 200`.

**`Summary` rules** (computed in `readstore.summarize(eventName, attrs []byte) string`):

| event_name              | Summary                                                            |
|-------------------------|--------------------------------------------------------------------|
| `claude_code.user_prompt` | `prompt: <length>ch[ /<command_name>]`                           |
| `claude_code.tool_result` | `<tool_name> <duration_ms>ms[ ✗]` (✗ if `success == false`)      |
| `claude_code.tool_decision` | `<decision> <tool_name>`                                       |
| `claude_code.api_request` | `<model> $<cost_usd>`                                            |
| `claude_code.api_error` | `error: <error or status_code>`                                    |
| anything else            | event_name as-is                                                   |

Summary truncates to 60 runes with `…`.

### `PromptDetail(ctx, db, promptID string) (PromptDetail, error)`

Two queries:

```sql
SELECT prompt_id, session_id, started_at, ended_at, prompt_length,
       command_name, command_source, cost_usd,
       input_tokens, output_tokens, cache_read_tokens, cache_creation_tokens,
       api_requests, subagent_requests, tool_calls, had_error
FROM prompts
WHERE prompt_id = ?;
```

```sql
SELECT ts, event_name, attrs
FROM events
WHERE prompt_id = ?
ORDER BY ts;
```

The second result is partitioned in Go into:
- `ToolCalls []ToolCall{TS, ToolName, DurationMS, Success}` (from `tool_result`)
- `APIRequests []APIRequest{TS, Model, CostUSD, InputTokens, OutputTokens}` (from `api_request`)
- Other event types are dropped from the prompt-detail view (out of scope).

Returns `ErrNotFound` (sentinel) if the prompt row is missing.

## Refresh Cadence

All three pages emit `tea.Tick(1 * time.Second)` and use the same in-flight de-dup pattern as `dashboard.Model`:

- **Sessions list:** ticks refresh the *first page only* (`cursor == nil`). When the user has paged forward, ticks are skipped (page contents are a frozen snapshot).
- **Session detail:** ticks fetch the latest 200 events. Selection sticks to the same event by `(ts, event_name)` if it still exists, else the top.
- **Prompt detail:** ticks refetch the prompt row + events. Cheap; `prompt_id` is indexed.

## Key Bindings

Global keys (`q`, `b`, `r`, `?`) remain handled by `App.Update`. Each new view declares its own per-view bindings via `bubbles/key.Binding`:

| Key            | Sessions List       | Session Detail      | Prompt Detail        |
|----------------|---------------------|---------------------|----------------------|
| `↑` / `k`      | Move selection up   | Move selection up   | (no selection)       |
| `↓` / `j`      | Move selection down | Move selection down | (no selection)       |
| `pgup`         | Previous page       | Previous page       | —                    |
| `pgdn`         | Next page           | Next page           | —                    |
| `g`            | Top                 | Top                 | —                    |
| `G`            | Bottom              | Bottom              | —                    |
| `enter`        | Drill into session  | Drill into prompt (only on `user_prompt` rows) | —     |

Each view also implements `ShortHelp()` returning these bindings; the existing app chrome footer renders them automatically.

The dashboard adds one binding:

| Key   | Action                                       |
|-------|----------------------------------------------|
| `s`   | Push `sessions.NewList(pool)`                |

## Error Handling

- Query failure (timeout, sql error): the model returns a `app.ErrMsg{Err}`; the chrome renders it in the existing error region. Body falls back to last-known data; if no data has loaded, an explicit `failed to load — press r to retry` message is shown.
- Pool nil (`errNoPool`): mirrors dashboard handling — empty body + error chrome.
- `PromptDetail` returns `ErrNotFound` → view renders the "prompt not found" empty state, no chrome error.

## Out of Scope (v1)

- Filtering/search on Sessions list.
- Project grouping.
- CSV export, copy-to-clipboard.
- Live "follow tail" mode for an active session.
- Prompt text rendering (only rollup numbers and event lists).
- Mouse support.

## Risks

- **Live session ticks under load:** the ticker fetches 200 events every second. For a session emitting hundreds of events/second, this could fall behind. Mitigation: `_pragma=query_only(1)` + 500ms context cap means slow queries cancel; render falls back to last-known data. Acceptable for v1.
- **Cursor invalidation under deletion:** the retention pruner runs daily and deletes rows older than `started_at < now - 30d`. If a paged-forward cursor lands inside that window, the next page may return zero rows. Treated as "end of list" — pruner activity is rare and the user can press `g` to jump to top. No special handling.
- **`attrs` JSON cost:** `Summary` parses `attrs` for every row. With 200 rows × 1Hz ticker, this is ~200 JSON unmarshals/sec — negligible. Can revisit if it ever shows on a profile.
